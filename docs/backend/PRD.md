# GrowPilot 后端开发 PRD

版本：1.0 · 2026-10-27 · 状态：开发交接基线

## 1. 产品与交付边界

GrowPilot 帮助求职者选择职业方向，以多个真实岗位 JD 对照简历及共享经历库，针对差距形成有可核查经验来源的求职成长建议；由用户选择加入本轮计划，安排每日任务，提交成果并确认整理进经历库。

本交接以 `web/` 当前界面和本目录规则为基准。线上演示为 https://internpilot-career-workspace-20261026.valid-moose-4187.chatgpt.site 。源码基线为 Sites 提交 `ebc3939114a8984c5d803288f16bb85758cb7010`，包含最新小步骤进度与完成按钮联动。仓库中的本次 GitHub 提交同时包含本交接文档。

**当前是可交互前端原型，不是已上线的真实后端产品。** 演示账户、123456 验证码、模型回答、岗位采集及建议中的检索过程均为示例。资料目前保存在 localStorage 和 IndexedDB。现有 Worker/Python 接口是探索代码，不能直接作为生产身份验证、数据隔离、全网搜索及持久化能力使用。

已取消：投递、申请状态、投递历史、自动撰写简历。浏览器小鸟咕噜不是原生桌宠；系统级悬浮、网页关闭后的推送需要独立实现。

## 2. 用户与导航

目标用户：有求职方向但实践不足、同时考虑多个方向，需要将岗位差距转化为每日可执行行动的学生及初入职场者。

固定顺序：
1. 求职方向：目标岗位 → 能力对照。
2. 成长计划：投入安排 → 查看建议 → 选择加入本轮。
3. 今日任务：当天安排 → 日期日历 → 具体执行。
4. 我的积累：经历库、成果、信息与复盘。

第一次登录默认方向页；有进行中任务的再次登录默认今日页。教育、实习、项目、课程等经历由同一用户跨方向复用。方向间的参考岗位、匹配快照、建议、准备周期分开管理。

## 4. 功能规则及验收

### 4.1 身份、资料与导入

采用邮箱验证码登录。验证码哈希保存、有过期、单次使用、尝试次数和发送频率限制；生产中不得保留万能演示码。会话通过安全 Cookie；退出使服务端会话失效。所有资源按当前会话用户鉴权，不信任前端传入 userId。

演示模式与真实账户数据分开。导入旧本机记录需要用户预览条数并确认，包含原 ID 到新 ID 的映射，附件重传校验，支持幂等重试；不得把别人的演示资料当成真实简历事实。用户可导出自己的记录与文件。

### 4.2 获取岗位、收藏与要求

一键采集应根据方向、职位大类/细分、地点、求职类型等创建异步作业。筛选含关键词、城市/区域、实习/全职、薪资及计薪单位、经验、学历、行业、规模、融资阶段；缺失字段不当作满足。保留手动输入及原文。

来源优先公开接口、开放页面或授权接入；不把绕过登录、反爬或任意平台全量爬取作为验收条件。不可用来源显示原因和手动录入入口，不能回退假数据却显示采集成功。

同一职位用来源 ID 或规范 URL 幂等更新，保留内容版本；跨源疑似重复展示依据，避免误合并。每条包含 title/company/location/rawJD/sourceUrl/sourceName/fetchedAt/publishedAt（可能为空）。

方向文件夹可加入多个岗位，用户明确选出本轮参考 JD。例如收集10条、勾选6条，则匹配仅使用6条。文件夹词云默认展示该文件夹岗位总体要求，明确标示口径；能力对照使用勾选集合，二者不得混淆。

相近要求自动归并，不提供“合并”操作按钮。每组要求保留每一条 jobId、jobVersion、原句、位置、必备/加分和归并置信度。同一岗位在一个要求组中仅计一次。不能仅凭词相同合并不同含义；不可确认时保留不同要求。

验收：6条 JD 中重复的 SQL 要求合成一组，显示涉及岗位数与逐条原文；非重复要求单独匹配；更改勾选不污染其他方向。

### 4.3 简历、经历和能力匹配

支持 PDF、DOCX、TXT、Markdown 简历，扫描 PDF 进入 OCR；解析失败给原因与粘贴文本替代入口。成果格式可不限，但模型只处理受支持且成功解析的类型。上传、存储、解析成功是不同状态。

经历类型：教育经历、实习经历、项目经历、课程经历、科研经历、校园经历、技能与证书、其他经历。保留本人行动、方法、成果、时间、限制、来源资料及人工核查状态。

匹配由 AI 自动输出，不要求用户逐项确认才有结果；用户可纠正并补充材料。输出 supported/partial/missing/unclear，分别代表材料较充分、部分支撑、暂缺证据、信息不足。**没有写进材料不等于不会**；已有基础可同时列出进阶差距。

每项结果包含要求原句、本人材料逐字证据、依据位置、缺口、说明。不得编造经历、雇佣关系、完成成果和匹配百分比。解析失败或模型不可用显示失败，不伪造匹配。

匹配依赖 JD 集合、JD 版本、简历/经历版本及归并版本。输入变化后标记旧结果过期，人工点击重跑；不得静默覆盖已采用任务与成果。历史更正绑定输入快照，材料变化时需重新核对。

### 4.4 有依据的求职成长建议

从能力对照一键生成，对每个用户方向和具体缺口开展网页检索，不在固定少量案例池内挑选。可以有可信来源索引或缓存，但必须披露实际覆盖和时效。

来源类型包括经验分享、求职/转型案例、企业实践；课程文档是辅助学习材料，不能作为“学习必能就业”的效果证据。每条建议直接附来源，而非独立案例模块。

来源必须真实可打开，记录标题、URL、发布者、可获得的日期、抓取时间、相关段落、来源类型、适用条件与局限。说明“借鉴哪个行动，为什么能补足哪个岗位要求”，不能凭个案保证录用。引用找不到或不适用时标“依据不足/待补充”，不能编造引用或宣称全网覆盖。

建议字段含标题、差距/要求组、理由、已有基础、具体动作、预计时间、成果、完成标准、来源、学习链接、检索查询与检索状态。重复生成复用可兼容的建议，并保留用户调整与已采用版本。

生成建议不等于加入计划。成长计划页“加入本轮计划”变为“已加入本轮计划”，可取消；取消不删除建议、成果和已完成历史。支持自定义任务及本人补充参考材料。

### 4.5 时间、排程和日历

用户可自由设定准备天数（前端1–730天）、起止日期、每天时长。各方向准备周期独立，但所有方向共用每天总预算。任务时长加总不能在多个方向重复占用同一份时间。

优先依据：必备要求与岗位频次、差距、已有基础、前置依赖；展示可理解的理由。当前前端权重仅为确定规则样例，不强制成为正式 AI 算法。用户可调序，前置关系仍有效；循环依赖应整批失败并保留原日程。

每日任务切成适合当天时间的片段，保留约15%余量。调整今日剩余时间、改排序或重排，只更新未完成片段；已完成 ID、累计时长和成果保留。剩余0分钟顺延，不伪造完成。周期不足展示未排入内容。

日期按用户 IANA 时区处理，禁止仅用服务端 UTC 作为用户日历日。周视图从周一开始，月视图支持跨年/闰年/6周。没有具体开始时刻时按日期展示，不捏造时间段。清单和日历读取同一数据；已完成同步，取消采用的未完成项不再排程。

### 4.6 执行和右侧 AI

左侧显示目标、步骤、产出及完成操作，右侧全高助手固定输入区，对话独立滚动。提问示例位于输入框下方；问答不弹窗/跳页、不改任务状态。

会话绑定 user/direction/task/sourceStep；带入当前阶段、材料读取状态、匹配缺口、建议来源及已有对话。自由问答可连续追问，支持取消、超时重试、流式响应；保存消息与可展示来源摘要，不存储/展示隐藏推理。

AI 拆解先生成可编辑草稿，用户确认后成为小步骤。确认前不改变日程/原步骤/时长；采用后执行前可撤销，替换拆解撤销恢复上一版本进度。已执行后不能无提示丢弃进度。

小步骤列表嵌入同一任务卡片：已完成/正在进行/接下来、进度条、计数。“完成第X步，继续下一步”同步计数、高亮与做法；全部小步骤完成后仍需确认本次任务。每日片段完成、原阶段完成、整个成长任务完成、成果登记是不同事件；不得互相自动等同。累计片段达到阶段所需时长后才完成阶段。

### 4.7 成果登记与入库

必填：成果名称、描述、至少一种成果内容（文字/链接/文件，可组合）；过程、方法、感想选填。单文件当前上限15MB，应前后端一致。链接可多个，文件可多个，格式不限不意味着都能解析。

一个任务可登记多份阶段成果，任务未完成也可登记；保存成果不改变完成状态。解析未知或外部链接未读时显示“未解析/未读取”，不能声称读过。

“AI 整理加入经历库”先生成草稿，提供新增/补充已有经历选择、分类及可编辑内容。必须人工核查并明确确认后事务写入；重复确认同一请求不新增重复经历。关联 outcomeId、事实证据、版本和人工修改历史；更新旧经历时标识可能与新成果冲突的旧表述。

### 4.8 复盘和提醒

记录网上信息、面试思考、执行想法，支持来源URL、关联方向/任务、下一步；转为自定义任务前可编辑。咕噜提醒来自真实未完成片段。通知仅在用户授权后发送，支持时间/时区/关闭/去重/失败记录。系统级桌宠不在Web后端首期范围。

## 5. 非功能要求

账户隔离、私有对象存储、短期签名URL、最小化模型传输与明确同意；不得把简历、验证码、API Key 写日志或代码仓库。文件类型/体积检测、恶意文件处理、下载权限、远程URL获取防内网访问及重定向绕过。外部岗位/网页/附件文本是数据，不能作为越权工具指令。

异步采集/解析/模型/排程作业需可取消、幂等重试、有超时；记录 jobId、traceId、尝试次数、模型与提示版本、消耗和错误类别。结果结构校验失败不入库。状态与版本更改用乐观锁，重排及成果确认用事务。邮件、模型和爬取均设额度、限流和费用上限。

性能验收建议：普通读写p95<1秒（不含模型/外网），长任务即时返回202及jobId；模型耗时以真实供应商测量，不承诺固定秒数。用户可删除/导出个人资料，约定文件与备份保留策略。部署应分演示/测试/生产环境。

## 6. 开发分期与总验收

P0：真实身份与隔离 → 数据库/对象存储/旧记录导入 → 文件解析 → 手动JD与方向 → 聚合匹配 → 持久化计划/执行/成果及确认入库。

P1：真实公开岗位适配、开放网页证据检索、流式任务助手、共享预算排程、通知、观测和费用控制。

上线完整产品前，不得将未实现的采集/检索/AI结果去掉“示例”标记。仅部分接入时逐功能展示真实、处理中、失败、示例的状态。

端到端验收：真实账户A录入10条JD选6条 → 上传简历并解析 → 查看归并要求、已有能力/缺证据项 → 围绕缺口生成带来源建议 → 选择2项加入 → 设17天及共享每天90分钟 → 日历与清单一致 → 助手拆3步，采用后完成1步显示1/3 → 登记PDF+文字描述 → AI草稿人工修改确认入库 → 换另一方向复用经历 → 账户B无法访问A资源 → 退出A后会话失效。

待产品确认：首期接入的岗位来源和城市覆盖、网页搜索/模型供应商、邮件供应商、部署区域、存储保留期、提醒渠道。开发者应提出选型方案；本PRD不假装已经完成这些决策。
